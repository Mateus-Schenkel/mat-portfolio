Otimização de consulta SQL Server

Estudo de caso focado em identificar gargalos de performance, analisar a causa do problema e reestruturar uma consulta para melhorar sua eficiência.

SQL Server Performance Índices Execution Plan
01

Pergunta de negócio

Como identificar os clientes que mais geraram receita nos últimos 90 dias sem comprometer o tempo de resposta do dashboard?

02

Contexto do problema

Uma consulta utilizada para alimentar um relatório comercial apresentava aumento progressivo no tempo de execução conforme o volume de vendas crescia.

O objetivo da investigação foi identificar quais operações estavam causando maior custo ao SQL Server e reduzir o processamento sem alterar o resultado esperado pelo negócio.

03

Query original

Consulta utilizada antes da otimização.

Problema
SQL Query antiga 
SELECT
    c.IdCliente,
    c.Nome,
    c.Segmento,
    SUM(v.ValorTotal) AS Receita90Dias,
    COUNT(v.IdVenda) AS QuantidadeVendas
FROM dbo.Clientes c
INNER JOIN dbo.Vendas v
    ON v.IdCliente = c.IdCliente
WHERE
    CONVERT(DATE, v.DataVenda) >=
        CONVERT(DATE, DATEADD(DAY, -90, GETDATE()))
    AND UPPER(v.Status) = 'APROVADA'
GROUP BY
    c.IdCliente,
    c.Nome,
    c.Segmento
ORDER BY
    Receita90Dias DESC;
04

Investigação

Antes de alterar a consulta, o primeiro passo foi medir seu comportamento utilizando as estatísticas do SQL Server.

SQL Diagnóstico

SET STATISTICS TIME ON;

-- Executar a consulta analisada aqui

SET STATISTICS IO OFF;
SET STATISTICS TIME OFF;

Execution Plan

Verificação de operações de alto custo, scans e possíveis gargalos na estratégia utilizada pelo otimizador.

Logical Reads

Análise da quantidade de páginas lidas pelo SQL Server durante a execução da consulta.

Execution Time

Comparação do tempo de CPU e tempo total antes e depois da otimização.

05

Problemas encontrados

01

Função aplicada na coluna de data

O uso de CONVERT diretamente sobre DataVenda dificulta o aproveitamento eficiente de índices existentes.

02

Transformação do campo Status

Aplicar UPPER durante o filtro adiciona processamento e pode prejudicar estratégias eficientes de busca.

03

Estratégia de índice

A consulta dependia de colunas frequentemente utilizadas nos filtros, relacionamento e agregação.

06

Query otimizada

Reestruturação mantendo a mesma regra de negócio.

Solução
SQL Query otimizada 
DECLARE @DataInicial DATETIME2(0);

SET @DataInicial = DATEADD(DAY, -90, SYSDATETIME());

SELECT
    c.IdCliente,
    c.Nome,
    c.Segmento,
    SUM(v.ValorTotal) AS Receita90Dias,
    COUNT(*) AS QuantidadeVendas
FROM dbo.Vendas v
INNER JOIN dbo.Clientes c
    ON c.IdCliente = v.IdCliente
WHERE
    v.DataVenda >= @DataInicial
    AND v.Status = 'APROVADA'
GROUP BY
    c.IdCliente,
    c.Nome,
    c.Segmento
ORDER BY
    Receita90Dias DESC;
07

Estratégia de índice

Além da reescrita da consulta, foi avaliado um índice compatível com as colunas utilizadas pelo filtro e pelo processamento da consulta.

SQL Índice analisado 
CREATE INDEX IX_Vendas_Status_DataVenda_Cliente
ON dbo.Vendas (
    Status,
    DataVenda,
    IdCliente
)
INCLUDE (
    ValorTotal
);

Um índice não deve ser criado automaticamente apenas porque beneficia uma consulta. É necessário avaliar seletividade, volume de dados, frequência de escrita e demais workloads da tabela.

09

Conclusão técnica

O ganho de performance não veio simplesmente de escrever uma query menor, mas de entender como o SQL Server acessava os dados.

A combinação entre filtros SARGable, análise do plano de execução, estatísticas de I/O e estratégia adequada de índices permitiu reduzir o custo da consulta preservando a regra de negócio.
